# Architecture

This is a Home Assistant add-on repository (the layout HA's Add-on Store expects: `repository.yaml` at the root plus one directory per add-on, each with its own `config.yaml`).

- `repository.yaml` — repo-level metadata shown in the HA Add-on Store.
- `docs/` — this file plus [project.md](project.md), [roadmap.md](roadmap.md), [routines.md](routines.md), and `features/`, which holds one file per feature: [battery-control.md](features/battery-control.md), [live-readings.md](features/live-readings.md), [diagnostics.md](features/diagnostics.md).
- `site/` — the public documentation site (VitePress), published to <https://elias-ems.github.io/elias-ems/> by `.github/workflows/docs.yml`. Its own npm project, independent of `addon/`. `site/guide/` is hand-written for someone installing the add-on; the "Under the hood" section is *generated* at build time from this directory by `site/scripts/sync-docs.mjs`, which copies an explicit list of files and rewrites their links — `../../addon/...` and `../CLAUDE.md` become GitHub URLs, sibling docs become site pages. That is why `docs/` remains the single source of truth for how the thing works and `site/internals/` is gitignored: these files are rewritten by the daily architecture review, and a hand-copied second version would drift within days. Anything a rewrite rule doesn't recognise is left alone and VitePress's dead-link check fails the build on it. `site/test/` covers the rewriting itself with node's built-in test runner, since the dead-link check only sees the links that stay on the site; `site/` borrows Biome and TypeScript from `addon/node_modules` rather than installing its own, so `npm run lint` and `npm run typecheck` there need the add-on installed.
- `.github/workflows/` — one workflow, `docs.yml`: it builds the site on every pull request touching `site/`, `docs/` or the workflow itself (where it doubles as the link check, since a doc moving here is what breaks it) and deploys from `main`. Nothing here runs either project's own checks — both projects' `lint` and `typecheck`, the add-on's three test suites and the site's link-rewriting tests are all local-only, and both of `lefthook.yml`'s pre-commit jobs are Biome and nothing else. So a pull request confined to `addon/` currently gets no automated check at all, which is worth knowing before reading a green tick on one as more than "the docs still build".
- `.claude/` — `skills/` holds the procedure each scheduled routine runs, one directory per skill. Versioned here on purpose; the schedules that fire them are deliberately not repo state, see [routines.md](routines.md). `launch.json` is the editor's run configurations — `dev`, `dev:mock` and `start` for the add-on, plus one for the site's `docs:dev` on port 5174, each launched through `mise` so it gets the pinned Node. The ingress and end-to-end stacks are not among them: both are started by an npm script that brings up more than one process, which is not a shape a debug configuration attaches to.
- `lefthook.yml`, `mise.toml`, `.gitattributes` — the pre-commit hook, the pinned non-npm tools (Node, `gh`), and the LF line-ending pin. See [CLAUDE.md](../CLAUDE.md) for why each is shaped the way it is.
- `addon/` — the "Elias ems" app: a React Router 8 (React, TypeScript) app that becomes its UI.
  - `addon/config.yaml` — HA add-on manifest (slug, arch, ingress). The app is reached through HA's ingress on port 3000, not exposed directly. `arch` is `aarch64` and `amd64` only: Home Assistant dropped armv7, and Node 24 publishes no 32-bit ARM builds to base an image on.
  - `addon/Dockerfile` — multi-stage build on `node:24-alpine`: `npm run build` runs in a build stage, then `server.js`, `build/server` and `build/client` are copied into the runtime image, which installs its own dependencies with `--omit=dev` and runs `npm run start`. The devDependencies the build needs never reach it.
  - `addon/server.js` — the production entry point, and the only place that knows about ingress. A small custom Express server rather than `react-router-serve`, because the ingress prefix arrives per request and has to become a per-request `basename` and a rewritten asset manifest, neither of which `react-router-serve` can provide. Plain JavaScript: it is what Node runs directly, with no build step in front of it. What it does with the prefix, and why `trust proxy` must stay off, is in the Home Assistant ingress section of [CLAUDE.md](../CLAUDE.md).
  - `addon/app/` — app source.
    - `addon/app/routes/` — the pages and the endpoints they call (Remix-style file naming, wired up by `flatRoutes()` in `addon/app/routes.ts`). Route modules stay thin: a loader gathers, an action dispatches on the form's `intent`, and the parsing, validation and decisions all live in `lib/`. The exception is a rule that has to see the *other* stored records, which a pure model module cannot read: `settings.tsx` is where a battery title that would slugify onto another battery's event type is rejected, and where control is refused when nothing is steerable. That is where the next cross-record check goes too. `api.entities.tsx` and `api.diagnostics.tsx` return JSON, and `api.diagnostics[.]txt.tsx` a downloadable text file — the `[.]` is flat-routes escaping, and [features/diagnostics.md](features/diagnostics.md) says why a bare dot would break it. `api.readings.tsx` is the one long-lived route, holding a `text/event-stream` open per open dashboard. What it owns is the transport — the connection's lifetime, coalescing, the heartbeat, and unsubscribing when the tab closes — never what a reading says, which stays `readDashboard()`'s. See [features/live-readings.md](features/live-readings.md).
    - `addon/app/lib/` — the domain, in five layers. Nothing here imports from `routes/` or `components/`; the dependency only ever points this way.
      - **Models** — `grid.ts`, `batteries.ts`, `control.ts`, `pv-entities.ts`, `diagnostics.ts`: types, `parse*` validation, `normalize*`, and constants like `STRATEGIES`. Pure, and imported by the browser as well as the server, which is what lets the settings UI share validation and types with the code that stores the result. `entities.ts`, `readings.ts` and `settings-form.ts` hold the rest of what the routes and components hand each other — shapes, plus the helpers that only exist to read them. This is also where a JSON endpoint's response type belongs, not in the route: both ends of that request need it, and neither a component nor a route may import from the other.
      - **Persistence** — `store.server.ts` holds the JSON storage every concern uses (`readJson`/`writeJson`, plus `createJsonCollection` for the id-addressed lists), with one thin `*.server.ts` per model: `grid.server.ts`, `batteries.server.ts`, `control-config.server.ts`, `pv-entities.server.ts`. One file per concern under the add-on's data directory, so a corrupt file can only take out its own feature.
      - **Diagnostics** — `diagnostics.ts` is the shared entry shape (origin, message, timestamp) plus the download's formatting, and `diagnostics.server.ts` is the in-memory ring buffer behind it, one per origin. Every feature logs here rather than keeping a log of its own; see [features/diagnostics.md](features/diagnostics.md).
      - **Home Assistant** — two modules talk to HA, both through the Supervisor's proxy: `ha.server.ts` asks its REST API, either for one entity at a time or for the whole `/states` list the settings forms pick from, and fires events on Home Assistant's bus — the one way this add-on asks for anything to change. An event rather than a service call because a service call writes to an entity, and a target per tick would leave a state change, a logbook line and a recorder row behind every few seconds; the event carries the same instruction and nothing stores it, with an automation deciding what the hardware actually wants. `ha-live.server.ts` holds a WebSocket subscribed to every state change, keeping a cache that answers with no round trip at all. `states.server.ts` is the one door in front of both for a *reading* — cache when it can, REST when it can't — and every read it returns says which source answered and when that value last changed. `readings.server.ts` turns a raw state into either a display string or a number, `entities.server.ts` turns the whole-list read into the sensors the pickers offer (which entities are offerable, what a picked one is called, how many a dropdown can show), and `dashboard.server.ts` assembles the home page's readings. It also owns the single list of entities that page depends on, which is what the stream watches; reading and watching are one list precisely because two would drift apart silently. Anything that needs a live value goes through `states.server.ts` rather than fetching for itself, which is what keeps the dashboard and the control loop agreeing about what the house is doing. See [features/live-readings.md](features/live-readings.md).
      - **Control runtime** — `net-zero.ts` is the strategy: a pure function of the current readings, no clock, no disk, no HA, which is what makes the decisions directly testable. `control-loop.server.ts` feeds it, started once at boot, and ticks when Home Assistant says one of its entities moved rather than on a clock — the configured interval is the rate limit on that, with a slow idle tick so a quiet house still proves the loop is alive. It owns its own entity list, smaller than the page's, and derives it from one read of the stored configuration per tick, the same way `dashboard.server.ts` derives the page's, so the ids a tick reads and the settings it decides with always describe the same house. That list is only ever inputs — whatever an automation touches on the way to the hardware must not provoke the next tick, or every target would feed straight back into publishing another. What it decides goes to `targets.server.ts`, which publishes it as an `elias_ems_<battery>_target_power` event — one type per battery, named after its title — and to diagnostics. `targets.server.ts` is also the one part of the control runtime that remembers anything: an event has no read-back, so what was last published per battery is held in the process, and both the deadband that suppresses a repeat and the periodic restatement that keeps that memory from becoming an indefinite assumption compare against it.
      - The `.server` suffix means "must never reach the client bundle", not "writes to disk" — `control-loop.server.ts`, `ha-live.server.ts`, `targets.server.ts` and `diagnostics.server.ts` all hold process state and no file, and the diagnostics buffers are in memory on purpose. See [features/battery-control.md](features/battery-control.md).
    - `addon/app/components/` — shared UI, with the settings sections under `components/settings/`. `DiagnosticsBox.tsx` is used twice with different scopes — filtered to battery control on the home page, unfiltered on Tools — which is why it takes an origin rather than being two components; anything feature-specific goes in as children, which is how `LiveHealthFacts.tsx` sits inside the home page's copy without the Tools page inheriting it. `components/form.ts` holds the styles shared across them — the form controls, the card and the hint text — so a field looks the same wherever it is used. It is not the only file that reads a `var(--color-*)`: a component styles itself inline and reaches for whichever tokens it needs, and what is common to all of them is the token, never a literal colour (see the Theming section of [CLAUDE.md](../CLAUDE.md)). `AppHeader.tsx` is the add-on's own top bar (name, then the pages) — Home Assistant renders an ingress panel as a bare iframe and offers no toolbar to add to, so an add-on that looks like it extends HA's chrome is really drawing its own; see the ingress section of [CLAUDE.md](../CLAUDE.md).
    - `addon/app/root.tsx` — the document every page renders inside: the `<html>` shell, the top bar, and the two things the theme depends on being here rather than anywhere else — the side-effect `import "./app.css"` and the `<meta name="color-scheme">` that beats the stylesheet to the first paint. Both are traps with a history; see the Theming section of [CLAUDE.md](../CLAUDE.md).
    - `addon/app/entry.server.tsx` — the stock React Router server entry, owned here because it is the only module loaded exactly once at server start, which is where the control loop is started.
    - `addon/app/app.css` — the only stylesheet: the light/dark colour tokens every component reads. Components still style themselves inline, but always through a `var(--color-*)`, never a literal colour — see the Theming section of [CLAUDE.md](../CLAUDE.md).
  - `addon/test/` — `unit/` (Vitest, no build), `integration/` (the real `server.js` behind a mock ingress proxy, over HTTP) and `e2e/` (the same stack in Chromium). The harness sitting beside them — `ha-mock.js`, `ingress-proxy.js`, `stack.js`, `dev.js`, `listen.js`, plus the `fixtures/` the mock serves its states from — is plain JavaScript for the same reason `server.js` is, and doubles as the local development stack. Each stack owns its own block of ports; [CLAUDE.md](../CLAUDE.md) says which, and why they must not overlap.
  - `addon/react-router.config.ts`, `addon/vite.config.ts`, `addon/tsconfig.json` — framework, bundler, and TypeScript config. `addon/vitest.config.ts` and `addon/playwright.config.ts` are separate from the Vite config on purpose (each file explains why); `addon/biome.json` configures Biome, which is both linter and formatter here — there is no ESLint and no Prettier, and [CLAUDE.md](../CLAUDE.md) covers why adding them isn't a small decision.
  - `.react-router/` (gitignored) — per-route types generated by `react-router typegen`, imported as `./+types/<route>`.

The first EMS feature, **battery control**, decides and acts: a loop reads the grid and battery entities, runs the net-zero-energy strategy, publishes each battery's target as a Home Assistant event, and logs both halves. A user-written automation is what connects that event to the hardware, which is also what puts an inverter's mode — the thing that makes a target honoured at all — within reach without another configuration field. What no automation can fix is that the add-on hears nothing back: an event on the bus is not proof anything acted on it. See [features/battery-control.md](features/battery-control.md) for the config model, the sign conventions, the strategy, the event payload and what is still missing.

The app has three pages. **Home** shows live readings for the configured PV arrays, the grid and the batteries, plus battery control's own diagnostics; **Tools** shows every feature's diagnostics merged, and can hand the log over as a text file; **Settings** configures all four concerns. The readings are pushed rather than polled: Home Assistant tells the add-on over a WebSocket that something moved, and the add-on tells every open dashboard over a server-sent-events stream. Polling the home loader every five seconds remains as the fallback for when that stream can't be established, since the numbers are only worth showing if they are current. See [features/live-readings.md](features/live-readings.md) and [features/diagnostics.md](features/diagnostics.md). PV curtailment and price integration (see [roadmap.md](roadmap.md)) aren't started.
