# Architecture

This is a Home Assistant add-on repository (the layout HA's Add-on Store expects: `repository.yaml` at the root plus one directory per add-on, each with its own `config.yaml`).

- `repository.yaml` — repo-level metadata shown in the HA Add-on Store.
- `docs/` — this file plus [project.md](project.md), [roadmap.md](roadmap.md), [routines.md](routines.md), and one `feature-*.md` per feature.
- `.claude/skills/` — the procedure each scheduled routine runs, one directory per skill. Versioned here on purpose; the schedules that fire them are deliberately not repo state, see [routines.md](routines.md).
- `lefthook.yml`, `mise.toml`, `.gitattributes` — the pre-commit hook, the pinned non-npm tools (Node, `gh`), and the LF line-ending pin. See [CLAUDE.md](../CLAUDE.md) for why each is shaped the way it is.
- `addon/` — the "Elias ems" app: a React Router 8 (React, TypeScript) app that becomes its UI.
  - `addon/config.yaml` — HA add-on manifest (slug, arch, ingress). The app is reached through HA's ingress on port 3000, not exposed directly. `arch` is `aarch64` and `amd64` only: Home Assistant dropped armv7, and Node 24 publishes no 32-bit ARM builds to base an image on.
  - `addon/Dockerfile` — multi-stage build on `node:24-alpine`: `npm run build` runs in a build stage, then `server.js`, `build/server`, `build/client`, and prod deps are copied into the runtime image, which runs `npm run start`.
  - `addon/server.js` — the production entry point, and the only place that knows about ingress. A small custom Express server rather than `react-router-serve`, because the ingress prefix arrives per request and has to become a per-request `basename` and a rewritten asset manifest, neither of which `react-router-serve` can provide. Plain JavaScript: it is what Node runs directly, with no build step in front of it. What it does with the prefix, and why `trust proxy` must stay off, is in the Home Assistant ingress section of [CLAUDE.md](../CLAUDE.md).
  - `addon/app/` — app source.
    - `addon/app/routes/` — the pages and the JSON endpoints (Remix-style file naming, wired up by `flatRoutes()` in `addon/app/routes.ts`). Route modules stay thin: a loader gathers, an action dispatches on the form's `intent`, and the parsing, validation and decisions all live in `lib/`.
    - `addon/app/lib/` — the domain, in four layers. Nothing here imports from `routes/` or `components/`; the dependency only ever points this way.
      - **Models** — `grid.ts`, `batteries.ts`, `control.ts`, `pv-entities.ts`: types, `parse*` validation, `normalize*`, and constants like `STRATEGIES`. Pure, and imported by the browser as well as the server, which is what lets the settings UI share validation and types with the code that stores the result. `entities.ts`, `readings.ts` and `settings-form.ts` are the shared shapes the routes and components hand each other.
      - **Persistence** — `store.server.ts` holds the JSON storage every concern uses (`readJson`/`writeJson`, plus `createJsonCollection` for the id-addressed lists), with one thin `*.server.ts` per model: `grid.server.ts`, `batteries.server.ts`, `control-config.server.ts`, `pv-entities.server.ts`. One file per concern under the add-on's data directory, so a corrupt file can only take out its own feature.
      - **Home Assistant** — `ha.server.ts` is the only module that talks to HA, through the Supervisor's proxy to its REST API; `readings.server.ts` turns a raw state into either a display string or a number. Anything else that needs a live value goes through these two rather than fetching for itself.
      - **Control runtime** — `net-zero.ts` is the strategy: a pure function of the current readings, no clock, no disk, no HA, which is what makes the decisions directly testable. `control-loop.server.ts` is the interval that feeds it and is started once at boot. `control-log.server.ts` is the debug trace it writes.
      - The `.server` suffix means "must never reach the client bundle", not "writes to disk" — `control-loop.server.ts` and `control-log.server.ts` hold process state and no file, and `control-log.server.ts` is an in-memory ring buffer on purpose. See [feature-battery-control.md](feature-battery-control.md).
    - `addon/app/components/` — shared UI, with the settings sections under `components/settings/`. `components/form.ts` holds the styles shared across them, which is also where the `var(--color-*)` lookups live rather than being repeated per component. `AppHeader.tsx` is the add-on's own top bar (name, then the pages) — Home Assistant renders an ingress panel as a bare iframe and offers no toolbar to add to, so an add-on that looks like it extends HA's chrome is really drawing its own; see the ingress section of [CLAUDE.md](../CLAUDE.md).
    - `addon/app/entry.server.tsx` — the stock React Router server entry, owned here because it is the only module loaded exactly once at server start, which is where the control loop is started.
    - `addon/app/app.css` — the only stylesheet: the light/dark colour tokens every component reads. Components still style themselves inline, but always through a `var(--color-*)`, never a literal colour — see the Theming section of [CLAUDE.md](../CLAUDE.md).
  - `addon/test/` — `unit/` (Vitest, no build), `integration/` (the real `server.js` behind a mock ingress proxy, over HTTP) and `e2e/` (the same stack in Chromium). The harness sitting beside them — `ha-mock.js`, `ingress-proxy.js`, `stack.js`, `dev.js`, `listen.js` — is plain JavaScript for the same reason `server.js` is, and doubles as the local development stack. Each stack owns its own block of ports; [CLAUDE.md](../CLAUDE.md) says which, and why they must not overlap.
  - `addon/react-router.config.ts`, `addon/vite.config.ts`, `addon/tsconfig.json` — framework, bundler, and TypeScript config. `addon/vitest.config.ts` and `addon/playwright.config.ts` are separate from the Vite config on purpose (each file explains why); `addon/biome.json` configures Biome, which is both linter and formatter here — there is no ESLint and no Prettier, and [CLAUDE.md](../CLAUDE.md) covers why adding them isn't a small decision.
  - `.react-router/` (gitignored) — per-route types generated by `react-router typegen`, imported as `./+types/<route>`.

The first EMS feature, **battery control**, is implemented as far as deciding: a loop reads the grid and battery entities on an interval, runs the net-zero-energy strategy, and logs what each battery should do. It does not yet write a setpoint to any battery. See [feature-battery-control.md](feature-battery-control.md) for the config model, the sign conventions, the strategy and what is still missing.

The app has a home page showing live readings for the configured PV arrays, the grid and the batteries plus the control loop's debug log, and a settings page for configuring all four. PV curtailment and price integration (see [roadmap.md](roadmap.md)) aren't started.
