# Architecture

The root `gym/` directory provides an offline battery-planner experiment harness.
The same benchmark is available in the EMS under **More → Benchmark**. Its
explicit Run all algorithms action evaluates every entry in the shared
`benchmark-algorithms.ts` registry against the fixed input and experiment settings
in `addon/app/lib/benchmark-data/`, bundled into the server build. The gym reads
those same files. The page compares energy cost, deadline and final charge,
target shortfall, ceiling changes and runtime for nominal and reduced solar,
with interval schedules below. The input table exposes solar, demand and both
tariffs for each interval, with battery model and reserve alongside. Edits are
local to the open page and can be reset to the bundled dataset. The action
validates the submitted values, keeps times/model/settings fixed, and returns
the input snapshot with its results. Subsequent edits mark those results stale.
Concurrent requests with identical inputs share one run; different inputs stay
isolated. Runs do not change live settings, stored plans or bundled files.
It runs the production pure optimizer directly with versioned JSON datasets;
the approved household dataset and frozen reference output are committed.
The test runs today's prepared inputs; yesterday is retained as historical context.
Raw captures and experiment results are gitignored. See `gym/README.md` in the
repository for replay and curation commands. A gym algorithm registry compares
the legacy cost optimizer with the production evening-target search using a
shared simulator; experiment settings are separate from the frozen dataset.

This is a Home Assistant add-on repository (the layout HA's Add-on Store expects: `repository.yaml` at the root plus one directory per add-on, each with its own `config.yaml`).

- `repository.yaml` — repo-level metadata shown in the HA Add-on Store.
- `docs/` — this file plus [project.md](project.md), [roadmap.md](roadmap.md), [routines.md](routines.md), and `features/`, which holds one file per feature: [battery-control.md](features/battery-control.md), [charge-limit.md](features/charge-limit.md), [live-readings.md](features/live-readings.md), [diagnostics.md](features/diagnostics.md), [dynamic-prices.md](features/dynamic-prices.md), [pv-curtailment.md](features/pv-curtailment.md). `plans/` is the one directory here that is not a description of how things are: it holds the design worked out before a change was built — today [docker-image-publishing.md](plans/docker-image-publishing.md) (the reasoning behind `image.yml` and the `image:` key) and [planner-data-export-benchmark.md](plans/planner-data-export-benchmark.md) (offline planner dataset export for the gym and sandbox). A plan stays after its change ships, because what it records is *why this shape and not the alternatives*, which the map and the feature docs deliberately do not carry. It is also the one directory `site/scripts/sync-docs.mjs` does not publish: the site describes the add-on to whoever installs it, and a rejected alternative is a question only somebody changing the code asks.
- `site/` — the public documentation site (VitePress), published to <https://elias-ems.github.io/elias-ems/> by `.github/workflows/docs.yml`. Its own npm project, independent of `addon/`. `site/guide/` is hand-written for someone installing the add-on; the "Under the hood" section is *generated* at build time from this directory by `site/scripts/sync-docs.mjs`, which copies an explicit list of files and rewrites their links — `../../addon/...` and `../AGENTS.md` become GitHub URLs, sibling docs become site pages. That is why `docs/` remains the single source of truth for how the thing works and `site/internals/` is gitignored: these files are rewritten by the daily architecture review, and a hand-copied second version would drift within days. Anything a rewrite rule doesn't recognise is left alone and VitePress's dead-link check fails the build on it. `site/test/` covers the rewriting itself with node's built-in test runner, since the dead-link check only sees the links that stay on the site; `site/` borrows Biome and TypeScript from `addon/node_modules` rather than installing its own, so `npm run lint` and `npm run typecheck` there need the add-on installed.
- `gym/` — the offline battery-planner experiment harness: versioned household datasets, algorithm runners, and benchmark reporting against the frozen reference output. See `gym/README.md`.
- `.github/workflows/` — three workflows. `docs.yml` builds the site on every pull request touching `site/`, `docs/` or the workflow itself (where it doubles as the link check, since a doc moving here is what breaks it) and deploys from `main`. `ci.yml` covers everything else on every pull request, in three jobs: `addon` (lint, typecheck, unit tests), `addon-integration` (one build, then the integration suite) and `site` (lint, typecheck, the link-rewriting tests). The end-to-end suite is the one thing still missing — its first CI run hung on the Playwright browser install rather than failing, so it is off until that is understood and stays a local-only `npm run test:e2e` in the meantime. It deliberately has no path filter — a filtered check reports nothing at all on a pull request that misses the filter, which is exactly the shape that leaves a required check hanging forever. `lefthook.yml`'s pre-commit jobs stay Biome and nothing else; CI is where the rest is enforced. See the continuous integration section of [AGENTS.md](../AGENTS.md) for why the runners are pinned, why Node's version lives in `.node-version`, and why a `node:24-alpine` container is the wrong runner here. `image.yml` builds and publishes the add-on's container image to `ghcr.io/elias-ems/elias-ems`, so Home Assistant pulls a prebuilt image instead of compiling the app on the user's own box. It runs on a published GitHub release, not on a merge to `main`: the release builds both architectures, pushes them, publishes the multi-arch manifest, and only then commits the new `version` into `addon/config.yaml` on `main` — the order that keeps `main` from ever advertising a version with no image behind it, since that is exactly what Supervisor reads to decide an update exists. See [Publishing the add-on image](../AGENTS.md#publishing-the-add-on-image) in AGENTS.md.
- `.claude/` — `skills/` holds the procedure each scheduled routine runs, one directory per skill. Versioned here on purpose; the schedules that fire them are deliberately not repo state, see [routines.md](routines.md). `launch.json` is the editor's run configurations — `dev`, `dev:mock` and `start` for the add-on, plus one for the site's `docs:dev` on port 5174, each launched through `mise` so it gets the pinned Node. The ingress and end-to-end stacks are not among them: both are started by an npm script that brings up more than one process, which is not a shape a debug configuration attaches to.
- `lefthook.yml`, `mise.toml`, `.node-version`, `.gitattributes` — the pre-commit hook, the pinned non-npm tools (`gh` in mise.toml, Node in `.node-version` so that CI and mise read the same number), and the LF line-ending pin. See [AGENTS.md](../AGENTS.md) for why each is shaped the way it is.
- `addon/` — the "Elias ems" app: a React Router 8 (React, TypeScript) app that becomes its UI.
  - `addon/config.yaml` — HA add-on manifest (slug, arch, ingress). The app is reached through HA's ingress on port 3000, not exposed directly. `arch` is `aarch64` and `amd64` only: Home Assistant dropped armv7, and Node 24 publishes no 32-bit ARM builds to base an image on. `image: "ghcr.io/elias-ems/elias-ems"` points Supervisor at the prebuilt multi-arch image `image.yml` publishes, rather than leaving the field unset and having Supervisor build the Dockerfile locally on install.
  - `addon/Dockerfile` — multi-stage build on `node:24-alpine`: `npm run build` runs in a build stage, then `server.js`, `build/server` and `build/client` are copied into the runtime image, which installs its own dependencies with `npm ci --omit=dev` and runs `npm run start`. Both stages use `npm ci` rather than `npm install`, so a published image is reproducible from `package-lock.json` rather than free to resolve outside it. The devDependencies the build needs never reach the runtime image, and the image itself is built and pushed by `image.yml` rather than by the user's own Home Assistant.
  - `addon/server.js` — the production entry point, and the only place that knows about ingress. A small custom Express server rather than `react-router-serve`, because two things about a request are known only once it arrives and both have to reach the build: the ingress prefix, which becomes a per-request `basename` and a rewritten asset manifest, and — where a proxy in front of Home Assistant reports one — the browser-facing host from `X-Forwarded-Host`, which becomes the build's `allowedActionOrigins` so that a save posted from a public name like Nabu Casa's is not rejected as cross-origin. `react-router-serve` can provide neither, and the build and handler caches are keyed on the pair rather than on the prefix alone for the same reason. Plain JavaScript: it is what Node runs directly, with no build step in front of it. What it does with each, why trusting that one header is safe here and would not be in general, and why `trust proxy` must nonetheless stay off, are in the Home Assistant ingress section of [AGENTS.md](../AGENTS.md).
  - `addon/app/` — app source.
    - `addon/app/routes/` — the pages and the endpoints they call (Remix-style file naming, wired up by `flatRoutes()` in `addon/app/routes.ts`). Route modules stay thin: a loader gathers, an action dispatches on the form's `intent`, and the parsing, validation and decisions all live in `lib/`. The exception is a rule that has to see the *other* stored records, or another concern's, which a pure model module cannot read: `settings.tsx` is where a battery or PV array title that would slugify onto another record's event type is rejected, and where control is refused when nothing is steerable and curtailment when nothing is curtailable or no price source is configured. That is where the next cross-record check goes too. Only the *reading* is the route's, though: what counts as a name clash is `titleSlugClashes` in `lib/slug.ts`, which the route hands the records it read, because the battery and the array need the identical comparison. `settings.tsx` is also effectful across both running loops: actions run under `withChargeLimitLock()`, invalidating active plans with `invalidateChargePlans()`, releasing restored charge power limits with `releaseChargeLimit()`, clearing commanded batteries with `releaseBatteries()`, and syncing the net-zero loop with `syncControlLoop()`. Pages comprise `_index.tsx` (the live dashboard), `plans.tsx` (modeled forecast timeline of demand, solar, battery behaviour and curtailment, offering an export download), `history.tsx` (historical state of charge, power and energy across 24h, 3d, 7d ranges), `settings.tsx`, `tools.tsx` (diagnostics log across all four origins and text download), `benchmark.tsx` (offline algorithm evaluation and dataset editor), and `playground.tsx` (component catalog against test fixtures). Endpoints are `api.readings.tsx` (SSE live stream and fallback snapshot), `api.entities.tsx` (allowlisted entity completions), `api.diagnostics.tsx` and `api.diagnostics[.]txt.tsx` (JSON and downloadable text logs), `api.charge-limits.ts` (JSON plan and lease status), and `api.planner-export[.]json.tsx` (exportable dataset for replay and benchmark). See [features/live-readings.md](features/live-readings.md) and [features/diagnostics.md](features/diagnostics.md).
    - `addon/app/lib/` — the domain, in seven layers. Nothing here imports from `routes/` or `components/`; the dependency only ever points this way.
      - **Models** — `grid.ts`, `batteries.ts`, `control.ts`, `curtailment.ts`, `pv-entities.ts`, `prices.ts`, `diagnostics.ts`: types, `parse*` validation, `normalize*`, and constants like `STRATEGIES`. Pure, and imported by the browser as well as the server, which is what lets the settings UI share validation and types with the code that stores the result. `slug.ts` is the one shared rule between two of them — reducing a title to something that can be part of an event type, and deciding whether a title collides with a record already stored, which both a battery and a PV array need to do identically, since two copies that drifted apart would leave the settings page showing one name and an automation needing another. It takes the records as an argument rather than reading them, which is what keeps it pure and usable from the browser. `charge-plan.ts` (interval calculations and `deviceLimit` clamping), `charge-evening.ts` (the pure evening-target optimization algorithm, replay, and validation), `charge-limit-status.ts` (status types and control state derivation), `energy-forecast.ts` (load profile construction and solar forecast aggregation), and `battery-history.ts` (history ranges and interval sampling) define the planner and history domains. `benchmark-algorithms.ts`, `benchmark-input.ts`, and bundled JSON in `benchmark-data/` configure offline algorithm comparisons. `entities.ts`, `readings.ts`, `settings-form.ts` and `dashboard.ts` hold the rest of what the routes and components hand each other — shapes, plus the helpers that only exist to read them. This is also where a JSON endpoint's response type belongs, not in the route: both ends of that request need it, and neither a component nor a route may import from the other. The same rule reaches past the type to any *argument* both ends have to agree on — `DECISION_ORIGINS` in `diagnostics.ts` is the pair of origins the home loader seeds the decision feed with and the feed's own poll then asks for, one constant because two copies would let the first paint and the first poll show different logs with nothing to raise an error about it. `dashboard.ts` is that rule's largest case — everything the home page draws, built by `dashboard.server.ts` and pushed again over the readings stream, so the route, the cards and the stream agree on one shape without a component reaching into a `.server` module for it. `dashboard-view.ts` sits beside it but reads that contract rather than defining it, and is described with the cards it feeds below. `playground-fixtures.ts` is the one module in this layer carrying data rather than shapes: the made-up readings, records and log entries `playground.tsx` draws every component against, including the states no configuration can produce — an unreadable sensor, a failed price feed, a loop enabled but not running. It belongs here by the test that decides this layer, being pure and safe for the browser, and it is held to that twice over: it takes the `now` its loader stamped rather than reading a clock, and every string a `.server` module would have formatted arrives already formatted, because otherwise the server's render and the browser's would disagree.
      - **Persistence** — `store.server.ts` holds the JSON storage every concern uses (`readJson`/`writeJson`, plus `createJsonCollection` for the id-addressed lists), with one thin `*.server.ts` per model: `grid.server.ts`, `batteries.server.ts`, `control-config.server.ts`, `curtailment-config.server.ts`, `pv-entities.server.ts`, `prices.server.ts`. It also persists `charge-limit-leases.json`, tracking active limit leases and restoration journals across restarts. One file per concern under the add-on's data directory, so a corrupt file can only take out its own feature.
      - **Diagnostics** — `diagnostics.ts` is the shared entry shape (origin, message, timestamp) plus the download's formatting, and `diagnostics.server.ts` is the in-memory ring buffer behind it, one per origin across four origins (`battery-control`, `pv-curtailment`, `prices`, `charge-limit`). Every feature logs here rather than keeping a log of its own; see [features/diagnostics.md](features/diagnostics.md).
      - **Home Assistant** — three modules talk to HA through the Supervisor's proxy: `ha.server.ts` asks its REST API (single entities, `/states`, or `fetchHaHistory`), fires events on the bus, and calls services like `setHaChargeLimit`; `ha-live.server.ts` holds a WebSocket subscribed to every state change, keeping a cache that answers with no round trip at all; and `ha-command.server.ts` holds a bounded WebSocket request/response connection for Energy preferences, solar forecasts, and recorder statistics. `states.server.ts` is the door in front of both for a *reading* — cache when it can, REST when it can't — and every read it returns says which source answered and when that value last changed. `readings.server.ts` turns a raw state into a display string, a number or a boolean — the last of those recognising literal `on` and `off` and nothing else, and returning null for everything from `unavailable` to a truthy-looking string, because a caller has to be able to tell "no car wants charge" from "we could not read the sensor" and the two do not lead to the same decision. `entities.server.ts` turns the whole-list read into the entities the pickers offer — one domain per request from a fixed allowlist (`sensor`, `binary_sensor`, or `number`). `energy-forecast.server.ts` queries preferences, solar forecasts, and historical consumption via `ha-command.server.ts`. `battery-history.server.ts` fetches recorder history via `fetchHaHistory` with TTL caching. `dashboard.server.ts` assembles the home page's readings. It also owns the single list of entities that page depends on, which is what the stream watches; reading and watching are one list precisely because two would drift apart silently. Anything that needs a live value goes through `states.server.ts` rather than fetching for itself, which is what keeps the dashboard and the control loop agreeing about what the house is doing. See [features/live-readings.md](features/live-readings.md).
      - **Control runtime** — two loops run at server start. `control-loop.server.ts` feeds `net-zero.ts` and `curtail.ts`, ticking when watched entities move (rate-limited by the configured interval, with an idle heartbeat). It publishes target power via `targets.server.ts` as `elias_ems_<battery>_target_power` events and curtailment limits via `pv-limits.server.ts` as `elias_ems_<array>_pv_limit` events. `syncControlLoop()` updates running state on save; `releasePvArray()` and `releasePvArrays()` release curtailment to 100%; `releaseBatteries()` commands 0W on deactivation or shutdown. The second loop, `charge-limit-loop.server.ts`, handles self-consumption charge-limit and discharge optimization: it coordinates with `charge-planner.server.ts` to compute plans from energy forecasts, dynamic prices, and battery configuration using the pure `charge-evening.ts` algorithm. It actuates maximum charge and AC output limits via `setHaChargeLimit`, tracks leases in `charge-limit-leases.json`, runs periodic readback every 30s and recalculates every 5m. `withChargeLimitLock()` serializes settings changes with actuation; `invalidateChargePlans()` resets plans on settings saves; `releaseChargeLimit()` restores native device limits when unconfigured, paused or removed. See [features/battery-control.md](features/battery-control.md), [features/pv-curtailment.md](features/pv-curtailment.md), and [features/charge-limit.md](features/charge-limit.md).
      - **Prices** — `price-formula.ts` is the little arithmetic language a tariff is written in (`((price * 1.02) + 0.1272) * 1.06`): a hand-written recursive-descent parser, pure, so the settings form previews a formula in the browser with the identical code the server evaluates it with. Hand-written rather than `new Function` because the formula comes off disk and compiling it to JavaScript would make a hand-edited `prices.json` arbitrary code execution in a container holding `SUPERVISOR_TOKEN`, and rather than a dependency because the grammar wanted is four operators and two functions. `price-source.server.ts` is the one door in front of wherever prices come from — today a Home Assistant entity, read through `states.server.ts` like every other entity so there is no transport of its own — and `price-format.server.ts` turns prices and slot boundaries into the strings a page shows. The contract is applied at *read* time rather than stored, so editing a formula takes effect on the next render rather than leaving every stored slot stale; and only the configuration is persisted, because while the source is an entity Home Assistant is already the store. See [features/dynamic-prices.md](features/dynamic-prices.md).
      - **Browser data** — `json-fetch.ts` is the odd one out in this list: not domain code but two hooks, `useFetchedJson` and `usePolledJson`, that read one of the app's own JSON routes with a plain `fetch` and keep the last good payload when a round fails. Everything the browser asks for in the background goes through them rather than through `useFetcher` or `useRevalidator`, for the reason the Failing well in the browser section of [AGENTS.md](../AGENTS.md) gives. They resolve their URL through `useHref`, which is what carries the ingress prefix a fetcher would have added for them. The one background request that is not one of them is the readings stream itself, which is an `EventSource` rather than a `fetch` and so has no hook here: `useLiveReadings` in `_index.tsx` owns the browser end of it — opening the stream, reading an error as "not delivering right now" rather than as the end of it, and letting the polled snapshot take over until a message comes back. It resolves its URL through `useHref` for the same reason, and the poll it falls back to is `usePolledJson` like everything else.
      - **Planner export & benchmark** — `planner-export.server.ts` serializes forecast intervals, load profiles, prices, and device configuration into versioned JSON datasets (`/api/planner-export.json`) for local replay in the documentation sandbox and the offline gym. `benchmark.server.ts` executes registered algorithms in `benchmark-algorithms.ts` against editable slot datasets (`BenchmarkDataset.tsx`) on the `/benchmark` route.
      - The `.server` suffix means "must never reach the client bundle", not "writes to disk" — `control-loop.server.ts`, `charge-limit-loop.server.ts`, `ha-live.server.ts`, `targets.server.ts`, `pv-limits.server.ts` and `diagnostics.server.ts` all hold process state, and the diagnostics buffers are in memory on purpose. See [features/battery-control.md](features/battery-control.md).
    - `addon/app/components/` — shared UI, with the settings sections under `components/settings/`, the home page and plans cards under `components/dashboard/`, and history charts under `components/history/`. Which subdirectory a component belongs in is decided by the component rather than by the page that happens to render it: a subdirectory holds one page's *composition* — the cards Home and Plans arrange, the sections Settings stacks, the history charts History mounts — and the top level holds the page-agnostic pieces those are built from, plus the shell's own `AppHeader.tsx` and the `form.ts` vocabulary below. Page-agnostic is a claim about what a component takes as props, not a count of the pages calling it today: besides `AppHeader.tsx`, that top level is `Field.tsx` and `EntityAutocomplete.tsx`, the two form controls settings sections are assembled from; `Measurement.tsx`, one live value with its label; `LiveStatus.tsx` and `LiveHealthFacts.tsx`, the status row and connection detail disclosure; `DiagnosticsBox.tsx`, the Tools log box; and `BenchmarkDataset.tsx`, the editable slot table for the benchmark page. Under `components/dashboard/`, `ChargePlanCard.tsx` and `PlanTimeline.tsx` draw the modeled energy plan and timeline, `chrome.ts` provides the card vocabulary, `dashboard-view.ts` in `lib/` decides strategy rail presentation, and `PriceChart.tsx` and the balance meter in `GridCard.tsx` are hand-drawn SVG pure functions of their props. `components/settings/` provides the settings vocabulary: `Section.tsx` is the card all sections are drawn in, `EditableList.tsx` owns the add / edit / remove mechanics, `useSectionEditor.ts` tracks open editor state per section, and `EventNameField.tsx` validates and previews slugified event names. `components/history/` holds `HistoryChart.tsx` for multi-day battery state and power history. `components/form.ts` holds the styles shared across form controls, cards and hints. `components/playground/` is the catalogue page's own chrome. `AppHeader.tsx` is the add-on's own top bar (Home, Plans, History, Settings, and a More menu with Benchmark, Tools, and Component playground); see the Home Assistant ingress section of [AGENTS.md](../AGENTS.md).
    - `addon/app/root.tsx` — the document every page renders inside, in three exports. `Layout` is the `<html>` shell and the top bar, plus the two things the theme depends on being here rather than anywhere else — the side-effect `import "./app.css"` and the `<meta name="color-scheme">` that beats the stylesheet to the first paint. Both are traps with a history; see the Theming section of [AGENTS.md](../AGENTS.md). The default export is the `<Outlet />` and nothing else, and `ErrorBoundary` is what anyone sees when a loader, an action or a navigation throws. The shell being its own export is what makes that boundary usable: React Router renders an error page inside the root `Layout` when there is one and inside a bare document of its own when there isn't, so without the split the error page arrives with no stylesheet, no navigation and no `Scripts` — which is what the framework's default "Application Error" screen was.
    - `addon/app/entry.server.tsx` — the stock React Router server entry, owned here because it is the only module loaded exactly once at server start, which is where both the battery control loop and charge limit loop are started.
    - `addon/app/app.css` — the only stylesheet: the light/dark colour tokens every component reads. Components still style themselves inline, but always through a `var(--color-*)`, never a literal colour — see the Theming section of [AGENTS.md](../AGENTS.md).
  - `addon/test/` — `unit/` (Vitest, no build), `integration/` (the real `server.js` behind a mock ingress proxy, over HTTP) and `e2e/` (the same stack in Chromium). The harness sitting beside them — `ha-mock.js`, `ingress-proxy.js`, `stack.js`, `dev.js`, `listen.js`, plus the `fixtures/` the mock serves its states from — is plain JavaScript for the same reason `server.js` is, and doubles as the local development stack. Each stack owns its own block of ports; [AGENTS.md](../AGENTS.md) says which, and why they must not overlap.
  - `addon/react-router.config.ts`, `addon/vite.config.ts`, `addon/tsconfig.json` — framework, bundler, and TypeScript config. `addon/vitest.config.ts` and `addon/playwright.config.ts` are separate from the Vite config on purpose (each file explains why); `addon/biome.json` configures Biome, which is both linter and formatter here — there is no ESLint and no Prettier, and [AGENTS.md](../AGENTS.md) covers why adding them isn't a small decision.
  - `.react-router/` (gitignored) — per-route types generated by `react-router typegen`, imported as `./+types/<route>`.

The first EMS feature, **battery control**, decides and acts: a loop reads the grid and battery entities, runs the net-zero-energy strategy, publishes each battery's target as a Home Assistant event, and logs both halves. A user-written automation is what connects that event to the hardware, which is also what puts an inverter's mode — the thing that makes a target honoured at all — within reach without another configuration field. What no automation can fix is that the add-on hears nothing back: an event on the bus is not proof anything acted on it. See [features/battery-control.md](features/battery-control.md) for the config model, the sign conventions, the strategy, the event payload and what is still missing.

**PV curtailment** is the second, and it rides on the same loop: while a kWh put on the grid earns less than a configured threshold, each curtailable array is held back — a modulating inverter to roughly what the house can absorb, and one that cannot be written to often to a single configured step for the whole episode — published as an `elias_ems_<array>_pv_limit` event. The two features share one snapshot per tick rather than reading separately, because both correct against the same grid meter and two reads would let their decisions describe different instants. Its arithmetic is a feedback form in which the load and the uncurtailable arrays cancel out, along with a battery that is *charging* — which is what gives the battery first refusal on a surplus with no coordination between the two. A battery that is **discharging** is the one term that does not cancel, and it is counted back into what the arrays may make: the grid reading is what crosses the meter after the battery has covered the house, so a discharging one hides the very shortfall the feedback term is looking for, and the two features would otherwise settle into a fixed point with the arrays pinned where they were last cut and the battery emptying to cover them. Curtailment reads the batteries' power for that and commands nothing to them. A charger following the meter — evcc in solar mode — reaches the same fixed point from the load side, and that one cannot be recovered inside the arithmetic the way a discharging battery can: a load throttled to nothing is indistinguishable from a load that was never there, so it has to arrive from outside the loop. While a configured "a car wants charge" sensor is on, the combined limit gets a floor under it of what the charger can take less whatever is generating that we are not modulating — a floor rather than an allowance, because the car's own draw is already inside the grid reading. The one thing to carry across from battery control is that the **safe direction is reversed**: a battery that goes blind should stop, an array that goes blind should generate, so every way of not knowing releases the arrays — with exactly one deliberate exception, that car sensor, where an unreadable state counts as no car and only warns, since releasing on it would spend generation in the one direction the feature exists to prevent. See [features/pv-curtailment.md](features/pv-curtailment.md).

**Charge-limit optimization** is the third: it optimizes a battery's maximum charging power and optional maximum AC output power while retaining native self-consumption mode. By restricting battery discharge during cheaper hours, stored energy is preserved for higher-priced evening and morning demand without requiring grid charging. It plans over rolling solar forecasts and consumption statistics using the pure Evening target algorithm, and actuates limits directly through Home Assistant number entities, tracking leases with periodic readback and restoration journals. See [features/charge-limit.md](features/charge-limit.md).

The app provides four primary pages in the top navigation, plus secondary tools in a More menu. **Home** is the dashboard: current kWh cost and earnings with production price charted against curtailment threshold; the real-time grid meter balance; the merged decision feed; the device status table; and the battery charge plan preview. **Plans** presents the full modeled forecast timeline (demand, solar, battery behaviour, and PV curtailment) and offers export of the planner dataset. **History** charts historical battery state of charge, power, and energy across selectable 24h, 3d, and 7d windows. **Settings** configures all six concerns in responsive multi-column cards. Under **More**, **Benchmark** runs registered optimization algorithms against editable datasets; **Tools** shows diagnostics merged across all four origins with a text log export; and **Component playground** renders every component against test fixtures inside Home Assistant's theme. All pages fill the ingress panel rather than sitting in a fixed column (see the Theming section of [AGENTS.md](../AGENTS.md)). Readings are pushed over a WebSocket-to-SSE stream with polling fallback. Background fetch requests use `json-fetch.ts` to keep last good state during connection blinks. Dynamic prices are imported and acted on by both PV curtailment and charge-limit planning (see [roadmap.md](roadmap.md)).

## Documentation planner sandbox

The public documentation site's `/planner` page imports version 1 planner
forecast exports and runs the production `charge-evening.ts` algorithm in a
browser worker. Files stay local. Users can adjust evening settings, inspect
forecast costs against unrestricted operation, view SoC and interval power
ceilings, and download the inputs together with the result. Device configuration
is context; the exported model and slots are the actual inputs for one battery.
The site runs its deployed algorithm version, so replay across versions can differ.

`site/lib/planner.ts` validates imported data and `site/test/planner.test.mjs`
checks production parity and malformed inputs. The docs deployment watches the
two shared planner modules so planner edits also rebuild the sandbox.
