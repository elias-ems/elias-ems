# Architecture

This is a Home Assistant add-on repository (the layout HA's Add-on Store expects: `repository.yaml` at the root plus one directory per add-on, each with its own `config.yaml`).

- `repository.yaml` — repo-level metadata shown in the HA Add-on Store.
- `docs/` — this file plus [project.md](project.md), [roadmap.md](roadmap.md), [routines.md](routines.md), and `features/`, which holds one file per feature: [battery-control.md](features/battery-control.md), [live-readings.md](features/live-readings.md), [diagnostics.md](features/diagnostics.md), [dynamic-prices.md](features/dynamic-prices.md), [pv-curtailment.md](features/pv-curtailment.md).
- `site/` — the public documentation site (VitePress), published to <https://elias-ems.github.io/elias-ems/> by `.github/workflows/docs.yml`. Its own npm project, independent of `addon/`. `site/guide/` is hand-written for someone installing the add-on; the "Under the hood" section is *generated* at build time from this directory by `site/scripts/sync-docs.mjs`, which copies an explicit list of files and rewrites their links — `../../addon/...` and `../CLAUDE.md` become GitHub URLs, sibling docs become site pages. That is why `docs/` remains the single source of truth for how the thing works and `site/internals/` is gitignored: these files are rewritten by the daily architecture review, and a hand-copied second version would drift within days. Anything a rewrite rule doesn't recognise is left alone and VitePress's dead-link check fails the build on it. `site/test/` covers the rewriting itself with node's built-in test runner, since the dead-link check only sees the links that stay on the site; `site/` borrows Biome and TypeScript from `addon/node_modules` rather than installing its own, so `npm run lint` and `npm run typecheck` there need the add-on installed.
- `.github/workflows/` — two workflows. `docs.yml` builds the site on every pull request touching `site/`, `docs/` or the workflow itself (where it doubles as the link check, since a doc moving here is what breaks it) and deploys from `main`. `ci.yml` covers everything else on every pull request, in three jobs: `addon` (lint, typecheck, unit tests), `addon-integration` (one build, then the integration suite) and `site` (lint, typecheck, the link-rewriting tests). The end-to-end suite is the one thing still missing — its first CI run hung on the Playwright browser install rather than failing, so it is off until that is understood and stays a local-only `npm run test:e2e` in the meantime. It deliberately has no path filter — a filtered check reports nothing at all on a pull request that misses the filter, which is exactly the shape that leaves a required check hanging forever. `lefthook.yml`'s pre-commit jobs stay Biome and nothing else; CI is where the rest is enforced. See the continuous integration section of [CLAUDE.md](../CLAUDE.md) for why the runners are pinned, why Node's version lives in `.node-version`, and why a `node:24-alpine` container is the wrong runner here.
- `.claude/` — `skills/` holds the procedure each scheduled routine runs, one directory per skill. Versioned here on purpose; the schedules that fire them are deliberately not repo state, see [routines.md](routines.md). `launch.json` is the editor's run configurations — `dev`, `dev:mock` and `start` for the add-on, plus one for the site's `docs:dev` on port 5174, each launched through `mise` so it gets the pinned Node. The ingress and end-to-end stacks are not among them: both are started by an npm script that brings up more than one process, which is not a shape a debug configuration attaches to.
- `lefthook.yml`, `mise.toml`, `.node-version`, `.gitattributes` — the pre-commit hook, the pinned non-npm tools (`gh` in mise.toml, Node in `.node-version` so that CI and mise read the same number), and the LF line-ending pin. See [CLAUDE.md](../CLAUDE.md) for why each is shaped the way it is.
- `addon/` — the "Elias ems" app: a React Router 8 (React, TypeScript) app that becomes its UI.
  - `addon/config.yaml` — HA add-on manifest (slug, arch, ingress). The app is reached through HA's ingress on port 3000, not exposed directly. `arch` is `aarch64` and `amd64` only: Home Assistant dropped armv7, and Node 24 publishes no 32-bit ARM builds to base an image on.
  - `addon/Dockerfile` — multi-stage build on `node:24-alpine`: `npm run build` runs in a build stage, then `server.js`, `build/server` and `build/client` are copied into the runtime image, which installs its own dependencies with `--omit=dev` and runs `npm run start`. The devDependencies the build needs never reach it.
  - `addon/server.js` — the production entry point, and the only place that knows about ingress. A small custom Express server rather than `react-router-serve`, because two things about a request are known only once it arrives and both have to reach the build: the ingress prefix, which becomes a per-request `basename` and a rewritten asset manifest, and — where a proxy in front of Home Assistant reports one — the browser-facing host from `X-Forwarded-Host`, which becomes the build's `allowedActionOrigins` so that a save posted from a public name like Nabu Casa's is not rejected as cross-origin. `react-router-serve` can provide neither, and the build and handler caches are keyed on the pair rather than on the prefix alone for the same reason. Plain JavaScript: it is what Node runs directly, with no build step in front of it. What it does with each, why trusting that one header is safe here and would not be in general, and why `trust proxy` must nonetheless stay off, are in the Home Assistant ingress section of [CLAUDE.md](../CLAUDE.md).
  - `addon/app/` — app source.
    - `addon/app/routes/` — the pages and the endpoints they call (Remix-style file naming, wired up by `flatRoutes()` in `addon/app/routes.ts`). Route modules stay thin: a loader gathers, an action dispatches on the form's `intent`, and the parsing, validation and decisions all live in `lib/`. The exception is a rule that has to see the *other* stored records, or another concern's, which a pure model module cannot read: `settings.tsx` is where a battery or PV array title that would slugify onto another record's event type is rejected, and where control is refused when nothing is steerable and curtailment when nothing is curtailable or no price source is configured. That is where the next cross-record check goes too. Only the *reading* is the route's, though: what counts as a name clash is `titleSlugClashes` in `lib/slug.ts`, which the route hands the records it read, because the battery and the array need the identical comparison. The second thing `settings.tsx` does beyond gathering and dispatching is *effectful* rather than a check, and it is the only place in the app besides boot that reaches into the running control loop: a saved configuration has to arrive at a loop that is already ticking, and a record that has just stopped being steered has to be let go of while it can still be named. Both are calls into `control-loop.server.ts` and are described with it below. `api.entities.tsx` and `api.diagnostics.tsx` return JSON, and `api.diagnostics[.]txt.tsx` a downloadable text file — the `[.]` is flat-routes escaping, and [features/diagnostics.md](features/diagnostics.md) says why a bare dot would break it. `playground.tsx` is the component playground — a catalogue of every component in the states that matter, including the ones a working installation never reaches; it has no data of its own beyond one `Date.now()` from its loader, and an action that absorbs the settings forms' posts and discards them. `api.readings.tsx` is the one long-lived route, holding a `text/event-stream` open per open dashboard, and answering `?snapshot=1` with the same readings once as JSON for when that stream isn't delivering. What it owns is the transport — the connection's lifetime, coalescing, the heartbeat, and unsubscribing when the tab closes — never what a reading says, which stays `readDashboard()`'s. See [features/live-readings.md](features/live-readings.md).
    - `addon/app/lib/` — the domain, in seven layers. Nothing here imports from `routes/` or `components/`; the dependency only ever points this way.
      - **Models** — `grid.ts`, `batteries.ts`, `control.ts`, `curtailment.ts`, `pv-entities.ts`, `prices.ts`, `diagnostics.ts`: types, `parse*` validation, `normalize*`, and constants like `STRATEGIES`. Pure, and imported by the browser as well as the server, which is what lets the settings UI share validation and types with the code that stores the result. `slug.ts` is the one shared rule between two of them — reducing a title to something that can be part of an event type, and deciding whether a title collides with a record already stored, which both a battery and a PV array need to do identically, since two copies that drifted apart would leave the settings page showing one name and an automation needing another. It takes the records as an argument rather than reading them, which is what keeps it pure and usable from the browser. `entities.ts`, `readings.ts`, `settings-form.ts` and `dashboard.ts` hold the rest of what the routes and components hand each other — shapes, plus the helpers that only exist to read them. This is also where a JSON endpoint's response type belongs, not in the route: both ends of that request need it, and neither a component nor a route may import from the other. The same rule reaches past the type to any *argument* both ends have to agree on — `DECISION_ORIGINS` in `diagnostics.ts` is the pair of origins the home loader seeds the decision feed with and the feed's own poll then asks for, one constant because two copies would let the first paint and the first poll show different logs with nothing to raise an error about it. `dashboard.ts` is that rule's largest case — everything the home page draws, built by `dashboard.server.ts` and pushed again over the readings stream, so the route, the cards and the stream agree on one shape without a component reaching into a `.server` module for it. `dashboard-view.ts` sits beside it but reads that contract rather than defining it, and is described with the cards it feeds below. `playground-fixtures.ts` is the one module in this layer carrying data rather than shapes: the made-up readings, records and log entries `playground.tsx` draws every component against, including the states no configuration can produce — an unreadable sensor, a failed price feed, a loop enabled but not running. It belongs here by the test that decides this layer, being pure and safe for the browser, and it is held to that twice over: it takes the `now` its loader stamped rather than reading a clock, and every string a `.server` module would have formatted arrives already formatted, because otherwise the server's render and the browser's would disagree.
      - **Persistence** — `store.server.ts` holds the JSON storage every concern uses (`readJson`/`writeJson`, plus `createJsonCollection` for the id-addressed lists), with one thin `*.server.ts` per model: `grid.server.ts`, `batteries.server.ts`, `control-config.server.ts`, `curtailment-config.server.ts`, `pv-entities.server.ts`, `prices.server.ts`. One file per concern under the add-on's data directory, so a corrupt file can only take out its own feature.
      - **Diagnostics** — `diagnostics.ts` is the shared entry shape (origin, message, timestamp) plus the download's formatting, and `diagnostics.server.ts` is the in-memory ring buffer behind it, one per origin. Every feature logs here rather than keeping a log of its own; see [features/diagnostics.md](features/diagnostics.md).
      - **Home Assistant** — two modules talk to HA, both through the Supervisor's proxy: `ha.server.ts` asks its REST API, either for one entity at a time or for the whole `/states` list the settings forms pick from, and fires events on Home Assistant's bus — the one way this add-on asks for anything to change. An event rather than a service call because a service call writes to an entity, and a target per tick would leave a state change, a logbook line and a recorder row behind every few seconds; the event carries the same instruction and nothing stores it, with an automation deciding what the hardware actually wants. `ha-live.server.ts` holds a WebSocket subscribed to every state change, keeping a cache that answers with no round trip at all. `states.server.ts` is the one door in front of both for a *reading* — cache when it can, REST when it can't — and every read it returns says which source answered and when that value last changed. `readings.server.ts` turns a raw state into a display string, a number or a boolean — the last of those recognising literal `on` and `off` and nothing else, and returning null for everything from `unavailable` to a truthy-looking string, because a caller has to be able to tell "no car wants charge" from "we could not read the sensor" and the two do not lead to the same decision. `entities.server.ts` turns the whole-list read into the entities the pickers offer (which entities are offerable, what a picked one is called, how many a dropdown can show) — one domain per request from a fixed allowlist, `sensor` for the fields picking a reading and `binary_sensor` for the one picking a state, so that a route reachable by URL cannot be pointed at the rest of the house — and `dashboard.server.ts` assembles the home page's readings. It also owns the single list of entities that page depends on, which is what the stream watches; reading and watching are one list precisely because two would drift apart silently. Anything that needs a live value goes through `states.server.ts` rather than fetching for itself, which is what keeps the dashboard and the control loop agreeing about what the house is doing. See [features/live-readings.md](features/live-readings.md).
      - **Control runtime** — `net-zero.ts` and `curtail.ts` are the strategies, one per feature: pure functions of the current readings, no clock, no disk, no HA, which is what makes the decisions directly testable. `control-loop.server.ts` feeds both, started once at boot, and ticks when Home Assistant says one of its entities moved rather than on a clock — the configured interval is the rate limit on that, with a slow idle tick so a quiet house still proves the loop is alive. Boot is not the only way in, and the three other entries are the whole of what this module offers the rest of the app. `settings.tsx` calls `syncControlLoop()` after saving either feature's configuration, so that ticking the box starts the feed moving now rather than at the next restart — and *un*ticking curtailment's is what releases the arrays, since the sync stops a loop that no longer has anything to run. It calls `releasePvArray()` for the one case a re-read of the configuration cannot cover: an array removed or un-ticked is gone from disk, or has lost the rating its limit was a percentage of, so the record as it stood *before* the edit is the only thing left that can name it, and without that call the last limit published for it would stand for ever. `_index.tsx` reads `controlLoopStatus()` and `curtailmentLoopStatus()` for the two strategy rails, and that is the only one of the three that changes nothing. Worth knowing before adding a steerable record type of a third kind: it needs the save hook *and* the release hook, and only the first is obvious from the settings form. It owns its own entity list, smaller than the page's, and derives it from one read of the stored configuration per tick, the same way `dashboard.server.ts` derives the page's, so the ids a tick reads and the settings it decides with always describe the same house. That list is only ever inputs — whatever an automation touches on the way to the hardware must not provoke the next tick, or every target would feed straight back into publishing another. What it decides goes to `targets.server.ts`, which publishes it as an `elias_ems_<battery>_target_power` event — one type per battery, named after its title — and to diagnostics. `targets.server.ts` is also where the battery half remembers what it has already said: an event has no read-back, so what was last published per battery is held in the process, and both the deadband that suppresses a repeat and the periodic restatement that keeps that memory from becoming an indefinite assumption compare against it. `curtail.ts` and `pv-limits.server.ts` are the same two roles for curtailment, and what each remembers differs in a way worth knowing. A limit is already quantised to whole percent by the strategy, so "the value changed" is exactly "it moved by at least one step" and there is no publish deadband. Nor is there a periodic restatement: a limit that stands unchanged is silent, because injection prices are positive most of the year and a timer restating "100%, generate freely" every half minute filled Home Assistant's activity log with thousands of identical events a day. What replaced it reads the array instead — `C + (G - G_target)` returns the same percent whether or not a limit is being obeyed, so only measured generation can tell an honoured limit from an ignored one, and an array making more than its limit plus a margin gets it re-asserted and logged as a warning. That is also the one place in the add-on that can currently notice an automation is not acting on what it was sent. How hard it presses depends on the inverter: a PV array carries a `controlMode`, and a `stepped` one — an inverter that commits every write to non-volatile memory, a Huawei SUN2000 being the common case — is commanded once when curtailment starts and once when it ends, drops out of the feedback law exactly the way an uncurtailable array does, ignores the price bands, and has its re-assertions capped so that a broken automation costs a bounded number of writes rather than one every five minutes. The warning still goes to the log on every tick, which is the split worth remembering: observe always, write rarely.
      - **Prices** — `price-formula.ts` is the little arithmetic language a tariff is written in (`((price * 1.02) + 0.1272) * 1.06`): a hand-written recursive-descent parser, pure, so the settings form previews a formula in the browser with the identical code the server evaluates it with. Hand-written rather than `new Function` because the formula comes off disk and compiling it to JavaScript would make a hand-edited `prices.json` arbitrary code execution in a container holding `SUPERVISOR_TOKEN`, and rather than a dependency because the grammar wanted is four operators and two functions. `price-source.server.ts` is the one door in front of wherever prices come from — today a Home Assistant entity, read through `states.server.ts` like every other entity so there is no transport of its own — and `price-format.server.ts` turns prices and slot boundaries into the strings a page shows. The contract is applied at *read* time rather than stored, so editing a formula takes effect on the next render rather than leaving every stored slot stale; and only the configuration is persisted, because while the source is an entity Home Assistant is already the store. See [features/dynamic-prices.md](features/dynamic-prices.md).
      - **Browser data** — `json-fetch.ts` is the odd one out in this list: not domain code but two hooks, `useFetchedJson` and `usePolledJson`, that read one of the app's own JSON routes with a plain `fetch` and keep the last good payload when a round fails. Everything the browser asks for in the background goes through them rather than through `useFetcher` or `useRevalidator`, for the reason the Failing well in the browser section of [CLAUDE.md](../CLAUDE.md) gives. They resolve their URL through `useHref`, which is what carries the ingress prefix a fetcher would have added for them. The one background request that is not one of them is the readings stream itself, which is an `EventSource` rather than a `fetch` and so has no hook here: `useLiveReadings` in `_index.tsx` owns the browser end of it — opening the stream, reading an error as "not delivering right now" rather than as the end of it, and letting the polled snapshot take over until a message comes back. It resolves its URL through `useHref` for the same reason, and the poll it falls back to is `usePolledJson` like everything else.
      - The `.server` suffix means "must never reach the client bundle", not "writes to disk" — `control-loop.server.ts`, `ha-live.server.ts`, `targets.server.ts`, `pv-limits.server.ts` and `diagnostics.server.ts` all hold process state and no file, and the diagnostics buffers are in memory on purpose. See [features/battery-control.md](features/battery-control.md).
    - `addon/app/components/` — shared UI, with the settings sections under `components/settings/` and the home page's cards under `components/dashboard/`. `DiagnosticsBox.tsx` is the Tools page's log; it still takes an origin rather than being one component per feature, because the home page used to mount two filtered copies of it and the parameter is what kept that from being two components. The home page now shows both loops in one `DecisionFeed.tsx`, which asks `api.diagnostics.tsx` for two origins at once and is open and polling rather than collapsed — the two loops act on the same meter within milliseconds, and the pair of decisions is the thing worth seeing. Under `components/dashboard/`, `chrome.ts` is the card vocabulary (the same role `form.ts` plays for the settings controls), `dashboard-view.ts` in `lib/` decides what each strategy row *says* — armed, curtailing, disabled — so that the rule with the edge cases is a tested pure function rather than a branch inside JSX, and `PriceChart.tsx` and the balance meter in `GridCard.tsx` are hand-drawn SVG with no charting dependency: they are two dozen rectangles and a handful of labels, and both are pure functions of their props, which is what keeps them hydrating quietly. `components/settings/` has the matching vocabulary on its own side: `Section.tsx` is the card all six sections are drawn in, and three more modules carry what only the two *id-addressed* sections — batteries and PV arrays — do. `EditableList.tsx` owns the add / edit / remove mechanics for both: the row shell, the three forms, the `<intent>-add`/`-update`/`-remove` names and which button says "Saving…", with the fields and the read-only summary arriving as render props, so a third record type of that shape is a section file rather than a third copy of the same forms. What it deliberately does not own is *which* row is open — that is `useSectionEditor.ts`, because putting a saved row back into its read-only state means knowing whether the action that just finished was this section's, which only the section can say. `EventNameField.tsx` is `slug.ts`'s browser end, showing the event type a title derives as it is typed and warning when an edit would orphan the name an automation is listening for; it is shared between the two for the same reason the rule below it is, since a second copy is the one that would quietly stop matching `slugifyTitle`. `components/form.ts` holds the styles shared across them — the form controls, the card and the hint text — so a field looks the same wherever it is used. It is not the only file that reads a `var(--color-*)`: a component styles itself inline and reaches for whichever tokens it needs, and what is common to all of them is the token, never a literal colour (see the Theming section of [CLAUDE.md](../CLAUDE.md)). `components/playground/` is the catalogue page's own chrome — the specimen frame and the viewport ruler — and the one directory here that no page of the add-on proper renders, which is why neither has a specimen of its own. `AppHeader.tsx` is the add-on's own top bar (name, then the pages) — Home Assistant renders an ingress panel as a bare iframe and offers no toolbar to add to, so an add-on that looks like it extends HA's chrome is really drawing its own; see the ingress section of [CLAUDE.md](../CLAUDE.md).
    - `addon/app/root.tsx` — the document every page renders inside, in three exports. `Layout` is the `<html>` shell and the top bar, plus the two things the theme depends on being here rather than anywhere else — the side-effect `import "./app.css"` and the `<meta name="color-scheme">` that beats the stylesheet to the first paint. Both are traps with a history; see the Theming section of [CLAUDE.md](../CLAUDE.md). The default export is the `<Outlet />` and nothing else, and `ErrorBoundary` is what anyone sees when a loader, an action or a navigation throws. The shell being its own export is what makes that boundary usable: React Router renders an error page inside the root `Layout` when there is one and inside a bare document of its own when there isn't, so without the split the error page arrives with no stylesheet, no navigation and no `Scripts` — which is what the framework's default "Application Error" screen was.
    - `addon/app/entry.server.tsx` — the stock React Router server entry, owned here because it is the only module loaded exactly once at server start, which is where the control loop is started.
    - `addon/app/app.css` — the only stylesheet: the light/dark colour tokens every component reads. Components still style themselves inline, but always through a `var(--color-*)`, never a literal colour — see the Theming section of [CLAUDE.md](../CLAUDE.md).
  - `addon/test/` — `unit/` (Vitest, no build), `integration/` (the real `server.js` behind a mock ingress proxy, over HTTP) and `e2e/` (the same stack in Chromium). The harness sitting beside them — `ha-mock.js`, `ingress-proxy.js`, `stack.js`, `dev.js`, `listen.js`, plus the `fixtures/` the mock serves its states from — is plain JavaScript for the same reason `server.js` is, and doubles as the local development stack. Each stack owns its own block of ports; [CLAUDE.md](../CLAUDE.md) says which, and why they must not overlap.
  - `addon/react-router.config.ts`, `addon/vite.config.ts`, `addon/tsconfig.json` — framework, bundler, and TypeScript config. `addon/vitest.config.ts` and `addon/playwright.config.ts` are separate from the Vite config on purpose (each file explains why); `addon/biome.json` configures Biome, which is both linter and formatter here — there is no ESLint and no Prettier, and [CLAUDE.md](../CLAUDE.md) covers why adding them isn't a small decision.
  - `.react-router/` (gitignored) — per-route types generated by `react-router typegen`, imported as `./+types/<route>`.

The first EMS feature, **battery control**, decides and acts: a loop reads the grid and battery entities, runs the net-zero-energy strategy, publishes each battery's target as a Home Assistant event, and logs both halves. A user-written automation is what connects that event to the hardware, which is also what puts an inverter's mode — the thing that makes a target honoured at all — within reach without another configuration field. What no automation can fix is that the add-on hears nothing back: an event on the bus is not proof anything acted on it. See [features/battery-control.md](features/battery-control.md) for the config model, the sign conventions, the strategy, the event payload and what is still missing.

**PV curtailment** is the second, and it rides on the same loop: while a kWh put on the grid earns less than a configured threshold, each curtailable array is held back — a modulating inverter to roughly what the house can absorb, and one that cannot be written to often to a single configured step for the whole episode — published as an `elias_ems_<array>_pv_limit` event. The two features share one snapshot per tick rather than reading separately, because both correct against the same grid meter and two reads would let their decisions describe different instants. Its arithmetic is a feedback form in which the load and the uncurtailable arrays cancel out, along with a battery that is *charging* — which is what gives the battery first refusal on a surplus with no coordination between the two. A battery that is **discharging** is the one term that does not cancel, and it is counted back into what the arrays may make: the grid reading is what crosses the meter after the battery has covered the house, so a discharging one hides the very shortfall the feedback term is looking for, and the two features would otherwise settle into a fixed point with the arrays pinned where they were last cut and the battery emptying to cover them. Curtailment reads the batteries' power for that and commands nothing to them. A charger following the meter — evcc in solar mode — reaches the same fixed point from the load side, and that one cannot be recovered inside the arithmetic the way a discharging battery can: a load throttled to nothing is indistinguishable from a load that was never there, so it has to arrive from outside the loop. While a configured "a car wants charge" sensor is on, the combined limit gets a floor under it of what the charger can take less whatever is generating that we are not modulating — a floor rather than an allowance, because the car's own draw is already inside the grid reading. The one thing to carry across from battery control is that the **safe direction is reversed**: a battery that goes blind should stop, an array that goes blind should generate, so every way of not knowing releases the arrays — with exactly one deliberate exception, that car sensor, where an unreadable state counts as no car and only warns, since releasing on it would spend generation in the one direction the feature exists to prevent. See [features/pv-curtailment.md](features/pv-curtailment.md).

The app has three pages, plus a fourth for whoever is working on it. **Home** is the dashboard, in the order the questions get asked: what a kWh earns and costs right now, with today's selling price charted against curtailment's threshold; then the meter, drawn against the target and deadband the strategies are aiming it at; then the two strategies side by side with one merged feed of what they have just decided; then every array and battery in a table. **Tools** shows every feature's diagnostics merged, and can hand the log over as a text file; **Settings** configures all six concerns, one card per concern, flowing into as many as three columns once the panel is wide enough. **Playground** is linked only from a Debug section at the foot of Tools rather than from the top bar: it renders every component against fixtures, which is where the two repo-wide rules — the light/dark tokens and the layout breakpoints — can be checked in one place, and inside a real ingress panel, which is the only place Home Assistant's own theme exists. All three pages fill the panel they are given rather than sitting in a fixed column — that is what Home Assistant's own panels do, and the readable measures belong to the cards inside them (see the Theming section of [CLAUDE.md](../CLAUDE.md)). The readings are pushed rather than polled: Home Assistant tells the add-on over a WebSocket that something moved, and the add-on tells every open dashboard over a server-sent-events stream. Asking the same route for a snapshot every five seconds remains as the fallback for when that stream can't be established, since the numbers are only worth showing if they are current. Every one of the browser's background requests — that fallback, the decision feed, the entity pickers — is a plain `fetch` through `lib/json-fetch.ts` rather than a fetcher or a revalidation, because a request that never comes back is a route error to React Router, and a route error is the whole page replaced by an error boundary. A dashboard left open in a tab should survive a connection that blinks. See [features/live-readings.md](features/live-readings.md) and [features/diagnostics.md](features/diagnostics.md). Price integration is imported but not yet acted on beyond curtailment (see [roadmap.md](roadmap.md)).
